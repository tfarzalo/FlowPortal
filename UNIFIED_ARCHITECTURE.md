# FlowPortal - Unified Single Architecture

## Overview

FlowPortal is now a **truly unified single-page application (SPA)** that uses **direct Supabase authentication and database queries**. There is NO separate backend server - everything runs in the frontend using Supabase's client library.

## Architecture

```
┌─────────────────────────────────────────┐
```

## Key Features

### 1. **Direct Supabase Authentication**
- Users log in using Supabase's built-in authentication
- JWT tokens are managed automatically by Supabase
- Admin users are identified by the `role` field in the `users` table

### 2. **Direct Database Queries**
- All CRUD operations use Supabase's client library
- No REST API endpoints needed
- Data transformation (snake_case ↔ camelCase) handled in service layer

### 3. **Direct Storage Access**
- Media files uploaded directly to Supabase Storage
- Public URLs generated by Supabase
- File metadata stored in the `media` table

### 4. **Single Deployment**
- Only frontend needs to be deployed (e.g., Netlify, Vercel)
- No backend server to maintain
- Environment variables: just `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`

## File Structure

### Service Layer (Direct Supabase Queries)

#### `/client/src/services/supabaseAdmin.ts`
Handles all admin operations:
- Site Settings (get, update)
- Pages (list, get, create, update, delete)
- Posts (list, get, create, update, delete)
- Users (list, get, update, delete)
- Dashboard Stats

#### `/client/src/services/supabaseForms.ts`
Handles form operations:
- Form Entries (list, get, update, delete, stats)
- Form Configurations (list, get by type, create, update, delete)
- Public Form Submission

#### `/client/src/services/supabaseMedia.ts`
Handles media operations:
- Upload to Supabase Storage
- List media files
- Get, update, delete media

### API Layer (Re-exports)

The `/client/src/api/` files now simply re-export functions from the service layer for backward compatibility:

- `/client/src/api/admin.ts` → re-exports from `supabaseAdmin.ts`
- `/client/src/api/forms.ts` → re-exports from `supabaseForms.ts`
- `/client/src/api/media.ts` → re-exports from `supabaseMedia.ts`

### Authentication Context

#### `/client/src/contexts/SupabaseAuthContext.tsx`
- Manages authentication state
- Listens for Supabase auth changes
- Loads user data from `users` table
- Provides login/logout functions
- Stores user role for admin access control

#### `/client/src/lib/supabase.ts`
- Initializes Supabase client
- Exports singleton instance for use throughout app

## Data Transformation

The service layer handles all data transformation:

### Frontend ↔ Database

**Frontend (camelCase)**:
```typescript
{
  siteName: "My Site",
  contactEmail: "info@example.com",
  isPublished: true
}
```

**Database (snake_case)**:
```sql
{
  site_name: "My Site",
  contact_email: "info@example.com",
  is_published: true
}
```

The `toCamelCase()` and `toSnakeCase()` utility functions in each service file handle this automatically.

## Setup Instructions

### 1. Supabase Project Setup

Create tables using the schema above, then set up Row Level Security (RLS):

```sql
-- Enable RLS on all tables
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE site_settings ENABLE ROW LEVEL SECURITY;
ALTER TABLE pages ENABLE ROW LEVEL SECURITY;
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;
ALTER TABLE media ENABLE ROW LEVEL SECURITY;
ALTER TABLE form_entries ENABLE ROW LEVEL SECURITY;
ALTER TABLE form_configurations ENABLE ROW LEVEL SECURITY;

-- Public read access for site_settings
CREATE POLICY "Public can read site settings"
  ON site_settings FOR SELECT
  USING (true);

-- Admin full access to site_settings
CREATE POLICY "Admins can update site settings"
  ON site_settings FOR ALL
  USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = auth.uid()
      AND users.role = 'admin'
    )
  );

-- Public read access for published pages
CREATE POLICY "Public can read published pages"
  ON pages FOR SELECT
  USING (is_published = true);

-- Admin full access to pages
CREATE POLICY "Admins can manage pages"
  ON pages FOR ALL
  USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = auth.uid()
      AND users.role = 'admin'
    )
  );

-- Similar policies for posts, media, etc.
-- Admin-only access for form_entries and form_configurations
```

### 2. Supabase Storage Setup

Create a storage bucket named `media`:

1. Go to Storage in Supabase dashboard
2. Create new bucket: `media`
3. Set it to **public** (for public URL access)
4. Set up storage policies:

```sql
-- Allow authenticated users to upload
CREATE POLICY "Authenticated users can upload media"
  ON storage.objects FOR INSERT
  TO authenticated
  WITH CHECK (bucket_id = 'media' AND auth.uid() IS NOT NULL);

-- Allow public read access
CREATE POLICY "Public can read media"
  ON storage.objects FOR SELECT
  TO public
  USING (bucket_id = 'media');

-- Admin can delete
CREATE POLICY "Admins can delete media"
  ON storage.objects FOR DELETE
  TO authenticated
  USING (
    bucket_id = 'media' AND
    EXISTS (
      SELECT 1 FROM users
      WHERE users.id = auth.uid()
      AND users.role = 'admin'
    )
  );
```

### 3. Create Admin User

In Supabase SQL Editor:

```sql
-- First create the auth user in Supabase Auth dashboard
-- Then insert into users table with admin role:

INSERT INTO users (id, email, role, first_name, last_name)
VALUES (
  'auth-user-uuid-here',  -- Get this from Supabase Auth dashboard
  'admin@example.com',
  'admin',
  'Admin',
  'User'
);
```

## Admin Access

### Login Flow

1. User navigates to `/login`
2. Enters email and password
3. Supabase authenticates the credentials
4. `SupabaseAuthContext` loads user data from `users` table
5. If `role = 'admin'`, user is redirected to `/admin`
6. If `role = 'user'`, access denied

### Admin Routes

All routes under `/admin` are protected by the `AdminLayout` component, which checks if the user is authenticated and has the `admin` role.

### Available Admin Features

- **Dashboard** (`/admin`) - View stats (pages, posts, users, form entries)
- **Pages** (`/admin/pages`) - Manage CMS pages
- **Posts** (`/admin/posts`) - Manage blog posts
- **Media** (`/admin/media`) - Upload and manage media files
- **Form Entries** (`/admin/form-entries`) - View and manage form submissions
- **Form Configuration** (`/admin/form-configuration`) - Configure forms
- **Users** (`/admin/users`) - Manage user accounts and roles
- **Settings** (`/admin/settings`) - Update site settings

## Security

### Row Level Security (RLS)

All database tables use RLS policies to ensure:
- Public can only read published content
- Only authenticated admins can create/update/delete
- Form submissions are admin-only

### Storage Policies

- Public read access to media files (for displaying on site)
- Only authenticated users can upload
- Only admins can delete

### Environment Variables

- `VITE_SUPABASE_ANON_KEY` is safe to expose (it's the "anon" key)
- Server-side operations require the service role key (not used in this architecture)
- All security is enforced by RLS policies in Supabase

## Benefits of This Architecture

1. **Simplicity** - No backend server to deploy/maintain
2. **Performance** - Direct database queries, no REST API overhead
3. **Scalability** - Supabase handles all scaling automatically
4. **Security** - Row Level Security at database level
5. **Cost** - Only pay for Supabase (Netlify free tier for hosting)
6. **Developer Experience** - Type-safe queries, automatic auth handling

## Migration from Backend Architecture

If you had a separate Express backend:

1. ✅ All backend service functions → `client/src/services/supabase*.ts`
2. ✅ All API routes → Direct Supabase queries
3. ✅ JWT auth middleware → Supabase Auth Context
4. ✅ File uploads → Supabase Storage
5. ✅ Database queries → `@supabase/supabase-js` client

## Troubleshooting

### "User not authenticated" errors

- Make sure user is logged in
- Check that Supabase session is valid
- Verify environment variables are set

### "Permission denied" errors

- Check RLS policies in Supabase
- Verify user has `admin` role in `users` table
- Ensure storage policies allow the operation

### Media upload fails

- Verify `media` storage bucket exists
- Check storage policies allow authenticated uploads
- Ensure bucket is set to public

### Can't login as admin

- Verify user exists in both Supabase Auth and `users` table
- Check that `role = 'admin'` in `users` table
- Verify email/password are correct

## Summary

FlowPortal is now a **unified single architecture** that combines frontend and "backend" into one cohesive application using direct Supabase integration. No separate backend server is needed - all authentication, database operations, and storage are handled directly from the React frontend via Supabase's client library.
